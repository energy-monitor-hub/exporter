# Оновлення експортера

[English](../UPDATES.md) · **Українська**

> Це переклад. Основна версія англійська ([docs/UPDATES.md](../UPDATES.md)); якщо тексти розходяться, правильна англійська.

Нові моделі й виправлення декодера приходять як підписані пакети декодерів
([DECODER_PACKS.md](DECODER_PACKS.md)), без нового образу. Ця сторінка про решту: нові версії
самого експортера.

## Як відбувається оновлення

З Docker Compose (`deploy/compose.yaml` без клону або `deploy/docker-compose.yml` у клоні) на
сторінці стану є кнопка **Оновити до vX.Y.Z**. Нічого не треба редагувати чи запускати.

- Експортер перевіряє список релізів: `EXPORTER_UPDATES=notify` (типово) або `off`;
  `EXPORTER_CHANNEL=stable` (типово) або `beta`;
  `EXPORTER_RELEASES_URL=https://<your-site>/releases/releases.json`. Без URL і довіреного ключа
  нічого не завантажується. Приблизно через хвилину після старту і далі щодня завантажує
  `releases.json` і підпис (Ed25519, ті самі ключі, що й для пакетів декодерів), відкидає
  прострочений або старіший список і порівнює версії. Запит не містить ідентифікаторів; хостинг
  бачить IP-адресу і час.
- Коли на твоєму каналі є новіша версія, сторінка стану про це каже і показує кнопку. Якщо
  поточну версію відкликано, банер червоний.
- Кнопка звертається до **оновлювача**, другого маленького контейнера з того самого образу.
  Експортер передає йому лише номер версії. Далі оновлювач сам:
  1. знову завантажує і перевіряє підписаний список релізів і бере з нього **digest** версії (лише
     не відкликану версію твого каналу, новішу за поточну);
  2. перевіряє **походження збірки в GitHub** (build provenance) для цього digest (пакет Sigstore з
     API атестацій GitHub): образ зібрав `exporter-image.yml` цього репозиторію з тегу `vX.Y.Z`;
  3. завантажує `ghcr.io/<owner>/<repo>@sha256:<digest>` і перевіряє, що це саме той digest;
  4. перестворює контейнер експортера з ним, зберігаючи том, порт, налаштування і мітки compose;
  5. чекає, доки новий експортер відповість новою версією (і отримуватиме дані зі станції, якщо
     старий отримував) і пропрацює 20 с; інакше видаляє його і знову запускає старий (**відкат**),
     усе в межах 4 хвилин.
- **Автоматичний режим** (перемикач на сторінці стану, типово вимкнений): оновлювач сам
  встановлює релізи `stable` (ніколи `beta`), перевіряє через 2 хвилини після старту і кожні
  6 годин. Версію, що не вдалася, день не пробує знову.
- Встановлену версію оновлювач пам'ятає у своєму томі. Пізніший `docker compose up` залишає
  оновлений контейнер; якщо щось перестворить експортер зі старішого образу, оновлювач поверне
  встановлену версію.
- Під час оновлення експортер перезапускається: приблизно хвилина без вимірів (черга на диску
  зберігається).

### Чому окремий контейнер

Щоб замінити контейнер, потрібен сокет Docker, а це root на хості. Експортер (мережа, твої
облікові дані, вебсторінка) його ніколи не отримує. Оновлювач має його і тому мінімальний:

- без опублікованого порту: відповідає лише в мережі compose і лише на адресу контейнера
  експортера; його API це `GET /status`, `POST /update {version}`, `POST /auto {enabled}`;
- запускає лише digest зі списку, підписаного довіреним ключем, з відповідним походженням збірки;
  експортер не може назвати образ;
- не отримує `.env`: URL списку релізів, канал і додаткові ключі читає з налаштувань контейнера
  експортера (процес експортера змінити їх не може);
- файлова система лише для читання, без Linux capabilities, `no-new-privileges`;
- звертається до URL списку релізів, `api.github.com` (атестації) і дзеркала TUF Sigstore
  (`tuf-repo-cdn.sigstore.dev`, корінь довіри; якщо воно недоступне, береться копія з образу).
  Образ з ghcr.io завантажує сам демон Docker.

Налаштування (shell або `.env` поруч із файлом compose): `ECOFLOW_UPDATER=0` вимикає оновлювач
(тоді сторінка пояснює, як оновитися вручну); `UPDATER_ATTESTATION=off` пропускає перевірку
походження (форки без атестацій, локальні реєстри); `DOCKER_SOCKET=/run/user/<uid>/docker.sock`
для rootless Docker або Podman.

Оновлювач оновлює експортер, а не себе: він змінюється рідко, а `docker compose pull &&
docker compose up -d` оновлює його разом з експортером.

### Вручну (без оновлювача, `docker run`, один виконуваний файл)

```bash
make exporter-update                                   # тег :main (у клоні)
# або закріпити точний реліз з банера (deploy/.env чи shell):
ECOFLOW_EXPORTER_IMAGE=ghcr.io/<owner>/<repo>@sha256:<digest> make exporter-update
```

Digest ніколи не змінюється, тож закріплений експортер лишається точно таким, доки ти не зміниш
рядок. З `docker run` один раз перейди на `deploy/compose.yaml` (README), щоб з'явилася кнопка.
Виконуваний файл оновлюється встановленням нового файлу з релізу ([NATIVE.md](NATIVE.md)).

## Випуск релізу (мейнтейнер)

1. Збільш `version` у `package.json` (і в lockfile: `npm version X.Y.Z --no-git-tag-version`),
   злий у `main`. Спершу саме це: тег на коміті з іншою версією валить збірку образу.
2. Постав на коміт злиття тег `vX.Y.Z` і запуш його (або створи реліз у GitHub з новим тегом на
   `main`). Щоб переробити хибний тег, видали і **тег**, а не лише реліз: реліз, опублікований
   знову на наявному тезі, бере той самий тег і нічого не збирає. `exporter-image.yml` звіряє тег з
   `package.json`, збирає amd64 + arm64 з **SLSA build provenance**, пушить `exporter:vX.Y.Z`
   (релізні теги ніколи не прибираються) і виводить digest та готовий запис для `releases.json`
   у підсумку запуску.
3. Додай запис у `releases/releases.json` з `"channel": "beta"` (pull request). Деплой вебу
   підписує і публікує його разом з дашбордом.
4. **Карантин**: через 7 днів без повідомлень про проблеми зміни на `"stable"` (ті самі 7 днів, що й
   правило npm у `CLAUDE.md`). Лише тоді стабільні експортери його бачать.
5. Аварійний вимикач: `"revoked": true` для поганого релізу. Експортери на ньому показують червоний
   банер, і його більше ніколи не пропонують.

`min_db_migration` це найновіша міграція, потрібна релізу на сервері. Застосуй міграції до того,
як позначати реліз стабільним.

## Перевірити образ вручну

```bash
docker buildx imagetools inspect ghcr.io/<owner>/<repo>@sha256:<digest> \
  --format '{{ json .Provenance }}'
```

Provenance називає репозиторій, коміт і workflow, що зібрав образ. Порівняй digest з тим, що в
`releases.json` і в підсумку релізного запуску.

## Ще не зроблено

- Оновлювач не оновлює сам себе (див. вище). Десктопний застосунок використовуватиме власний
  підписаний оновлювач платформи.
- Показ оновлення ще й на вебдашборді (зараз: сторінка стану і логи).
