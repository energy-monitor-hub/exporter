# Energy Monitor Hub: exporter

[English](README.md) · **Українська**

Невелика локальна програма, яка читає телеметрію з зарядної станції **EcoFlow** (зараз Delta 3 Max Plus) через приватний MQTT API EcoFlow, той самий, що в мобільному застосунку, декодує protobuf-повідомлення (напруги комірок, напруга й частота мережі, температури, SOH, балансування, відключення світла) і пише їх у **твій власний проєкт Supabase**, звідки їх читає дашборд.

Репозиторій публічний, щоб ти міг перевірити, що працює на твоїй машині: експортер — єдина частина, яка взагалі бачить твій пароль EcoFlow. Дашборд (веб-застосунок, схема бази, хостинг) живе в окремому репозиторії; вони перетинаються лише через [контракт з базою](docs/uk/DB_CONTRACT.md).

## Куди йдуть твої облікові дані

Перевір шляхи в коді сам; секрети потрапляють лише сюди:

| Секрет | Де використовується | Де зберігається |
|---|---|---|
| E-mail і пароль EcoFlow | надсилаються лише в API входу самого EcoFlow (`ECOFLOW_API_HOST`, за замовчуванням `api.ecoflow.com`), щоб отримати дані для MQTT: `src/auth/` | `.env` (якщо ти їх туди поклав) або `/data/credentials.json`, зашифровано AES-256-GCM: `src/secrets/` |
| Ключ до `credentials.json` | випадковий 256-бітний ключ, зберігається у твоєму проєкті Supabase окремо для кожного експортера (`exporter_key`), видається лише токену цього експортера, видаляється, коли ти його відкликаєш | ніколи не на томі |
| Серійний номер станції | MQTT-топіки в EcoFlow, `devices.sn` у твоєму Supabase | `.env` або `credentials.json` |
| Вхід у дашборд | OAuth 2.1 + PKCE у твій Supabase Auth; пароля від дашборда експортер не бачить | `/data/oauth.json` (`0600`) |

Авторам проєкту нічого не надсилається. Експортер говорить рівно з трьома видами хостів: EcoFlow (API входу і MQTT-брокер), проєкт Supabase твого дашборда і сам сайт дашборда: його `exporter.json` (який проєкт Supabase і публічний anon-ключ брати), підписані пакети декодера і список релізів (звичайні GET-запити без ідентифікаторів). Типово дашборд це розміщений дашборд проєкту (`https://energy-monitor-hub.web.app`, `src/destinations.ts`); картка **Where data goes** («Куди йдуть дані») на сторінці стану показує всі адреси (лише для читання). Перепис моделей і завантаження зразків (нижче) вимкнені, доки ти не дав згоду на сторінці стану, і йдуть у твій власний Supabase.

## Перевір, що запускаєш

- Образ і бінарники збирає GitHub Actions у цьому репозиторії ([exporter-image.yml](.github/workflows/exporter-image.yml), [exporter-binaries.yml](.github/workflows/exporter-binaries.yml)) з підписаним **build provenance attestation**, що прив'язує кожен digest образу і бінарник до коміту й workflow, які їх зібрали:
  ```bash
  gh attestation verify oci://ghcr.io/<owner>/<repo>@sha256:<digest> --repo <owner>/<repo>
  gh attestation verify ecoflow-exporter-linux-x64 --repo <owner>/<repo>
  ```
- Або збери сам з цих сирців: `docker compose -f deploy/docker-compose.yml up -d --build` чи `npm ci && npm run build && npm start`.
- Кожна залежність закріплена на точній версії й перевіряється на 7-денний карантин (нижче).

## Запис фікстур

Скрипт логіниться в EcoFlow як мобільний застосунок, підключається до MQTT і зберігає кожне повідомлення як є. Запускати локально (просто з Node 22 або в devcontainer): хмарний CI чи пісочниця до брокера зазвичай не дістає.

```bash
cp .env.example .env              # ECOFLOW_USERNAME, ECOFLOW_PASSWORD, DEVICE_SN
npm ci
make record                       # пише, доки не натиснеш Ctrl+C
make record ARGS="--minutes 20"   # або зупиниться сам
```

- Файли падають у `test/fixtures/<час-старту>/`: `00001-<час>-<cmdFunc>-<cmdId>.bin` і `index.json` (топік, тип, cmdFunc/cmdId кожного заголовка, розміри).
- SN, userId і серійники батарейних модулів замінюються на `XXXX…` / `0000…` тієї ж довжини, і в файлах, і в `index.json`. Перед комітом все одно глянь: `grep -rl "<твій SN>" test/fixtures` має нічого не знайти.
- На старті й далі кожні 5 хв скрипт просить пристрій надіслати всі значення (так робить застосунок і ioBroker). Вимкнути: `--no-quotas`, змінити період: `--quota-every 120` (секунди).
- Якщо логін не проходить на `api.ecoflow.com`, спробуй `ECOFLOW_API_HOST=api-e.ecoflow.com` у `.env`.
- Що записати: 10–15 хв звичайної роботи, заряд від мережі, розряд, і найцінніше: вимкнення й повернення мережі.
- Зв'язок рветься: mqtt.js перепідключається кожні 5 с; якщо брокер відхиляє креди, скрипт логіниться заново з наростаючою паузою (до 5 хв). Повідомлення під час обриву не пишуться.

## Продакшн-запуск експортера

### Підключити новий експортер (без клону і збірки)

Сторінка дашборду **«Експортери»** (`/exporters`) показує ці кроки з уже підставленими значеннями цього інстансу, тож новому користувачу лишається скопіювати й вставити. Без дашборду те саме вручну:

1. У порожню папку поклади [`deploy/compose.yaml`](deploy/compose.yaml) і запусти готовий образ (amd64 і arm64). Налаштовувати нічого не треба: він підключається до дашборду проєкту.

   ```bash
   curl -fsSLO https://raw.githubusercontent.com/<owner>/<repo>/main/deploy/compose.yaml
   docker compose up -d
   ```

   Так запускаються експортер і його оновлювач, тож нові версії встановлюються зі сторінки стану одним натиском ([docs/uk/UPDATES.md](docs/uk/UPDATES.md)). Звичайний `docker run` теж працює, але без кнопки:

   ```bash
   docker run -d --name ecoflow-exporter --restart unless-stopped \
     -p 127.0.0.1:9101:9101 -v ecoflow-exporter:/data \
     ghcr.io/<owner>/<repo>:main
   ```

   Без Docker натомість встанови однофайловий бінарник із релізу на GitHub ([docs/uk/NATIVE.md](docs/uk/NATIVE.md)).
2. На тій самій машині відкрий сторінку стану **http://127.0.0.1:9101/**, натисни **Log in**, увійди в дашборд і підтвердь запит.
3. На тій самій сторінці заповни картку **EcoFlow account** (e-mail і пароль застосунку, серійний номер станції). Дані підуть самі.

Усе, що зберігає експортер, лежить в одному томі `/data`: черга записів, токен входу, зашифровані облікові дані EcoFlow (ключ лишається в Supabase), останній `exporter.json` дашборду і кеш пакетів декодерів.

**Інші адреси (розробка):** експортер читає `<дашборд>/exporter.json` (його публікує збірка дашборду) з проєктом Supabase і anon-ключем і бере пакети декодерів і список релізів з того самого сайту. `.env` може направити його деінде: `DASHBOARD_URL=<сайт>` переносить усе разом, а `SUPABASE_URL` + `SUPABASE_ANON_KEY`, `DECODER_INDEX_URL` і `EXPORTER_RELEASES_URL` перекривають кожну адресу окремо (наприклад, локальний Supabase). Сторінка стану показує ці адреси, але змінити їх не дає. Перехід на інший проєкт Supabase означає новий вхід і повторне введення акаунта EcoFlow (старий вхід і ключ збережених облікових даних належать старому проєкту). Оновлення: натисни **Оновити до vX.Y.Z** на сторінці стану, коли вона це пропонує (з `docker run`: `docker pull` образу, `docker rm -f ecoflow-exporter` і запустити знову; або перейти на файл compose, він бере той самий том даних). Якщо пакет у ghcr приватний, спершу `docker login ghcr.io` (див. «Образ експортера в ghcr.io»).

### Через docker compose (з клону)

```bash
make exporter-update     # стягує готовий образ з ghcr.io (amd64 або arm64) і запускає його
# те саме без make:
docker compose -f deploy/docker-compose.yml pull
docker compose -f deploy/docker-compose.yml up -d
```

Так запускається й оновлювач: сторінка стану встановлює релізи одним натиском. Оновити натомість до свіжого `main`: знову `make exporter-update`. Образ свого форку: `export ECOFLOW_IMAGE_REPO=ghcr.io/<ти>/<repo>` (або в `deploy/.env`). `up -d --build` натомість збирає образ локально з поточного коду.

`.env` не потрібен; інші адреси для розробки див. вище. Ключ `service_role` експортеру не потрібен ніколи.

### Вхід експортера

Експортер пише в Supabase від імені користувача, який його підтвердив (OAuth 2.1 сервер Supabase, PKCE), і RLS дає йому писати лише пристрої цього користувача. Один раз на машині з експортером:

```bash
docker compose -f deploy/docker-compose.yml run --rm --service-ports login
# dev-стек (із сирців):
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.dev.yml run --rm --service-ports login
# без Docker: npm run login
```

1. Експортер реєструється як окремий OAuth-клієнт (назва з `OAUTH_CLIENT_NAME`, наприклад «Домашній сервер») і друкує посилання.
2. Відкрий його, увійди в дашборд і натисни «Дозволити» на сторінці `/oauth/consent`.
3. Браузер повертається на `http://127.0.0.1:9102/callback`, і вхід завершується сам. Якщо експортер на іншій машині і ця сторінка не відкрилась, скопіюй її адресу з адресного рядка й встав у термінал експортера.

Токени лежать у `/data/oauth.json` (той самий volume, що й буфер; файл секретний, `0600`). Запущений експортер підхоплює новий вхід сам, без перезапуску. Токен доступу живе годину, експортер оновлює його сам. Список підключених експортерів і кнопка «Відкликати» є на сторінці «Експортери» дашборду (`/exporters`). Після відкликання експортер не може оновити токен (щонайпізніше за годину), рядки чекають у буфері, а в `/healthz` видно `auth.state = revoked`: зроби вхід ще раз.

Пристрій з'являється в `devices` при першому записі (RPC `ensure_device`, до 10 пристроїв на користувача). Пристрій, записаний ще старим експортером з `service_role`, переходить до того, чий експортер першим надішле той самий серійний номер (або одразу до єдиного користувача проєкту, якщо він один).

### Налаштування акаунта EcoFlow

Замість `ECOFLOW_USERNAME`, `ECOFLOW_PASSWORD` і `DEVICE_SN` у `.env` їх можна ввести на сторінці стану (нижче). Не задавай їх у `.env`, запусти експортер і відкрий **http://127.0.0.1:9101/**:

1. **Увійди** (вхід у Supabase вище). Без нього форма недоступна: ключ шифрування зберігається разом із входом цього експортера.
2. Заповни картку **Акаунт EcoFlow**: e-mail і пароль акаунта застосунку, серійний номер станції, сервер (для EU-акаунтів можна обрати `api-e`). «Перевірити і зберегти» спершу входить в EcoFlow і нічого не зберігає, якщо вхід не вдався.
3. Експортер одразу підключається до станції. Після перезапуску він входить у Supabase, отримує ключ, розшифровує файл і підключається, нічого вводити не треба.

Як це захищено:

- Облікові дані зашифровані AES-256-GCM у `/data/credentials.json` (`CREDENTIALS_PATH`, `0600`). Випадковий 256-бітний ключ **не** лежить у volume: його зберігає Supabase, окремий для кожного експортера (`public.exporter_keys`), і віддає лише токену, виданому саме цьому експортеру (claim `client_id`), а не сесії вебзастосунку. Пароля сервер не бачить ніколи.
- **Відкликання експортера** на сторінці «Експортери» дашборду видаляє його ключ, тож будь-яка копія volume чи бекап стає непридатною. «Забути облікові дані» на сторінці стану видаляє і файл, і ключ.
- Форма налаштування відповідає лише через loopback-адресу (`127.0.0.1` / `localhost`), а нативно ще й лише на з’єднання з цього комп’ютера, навіть якщо `UI_ALLOWED_HOSTS` і `LISTEN_HOST` відкривають сторінку для локальної мережі.
- Чесні обмеження: поки експортер **не** відкликано, той, хто скопіює весь volume, має й `oauth.json` і може отримати ключ (ротація refresh-токена тоді виведе твій експортер із входу, це сигнал його відкликати). Шкідлива програма на тій самій машині може прочитати пам’ять процесу. Для перезапуску потрібен інтернет, щоб отримати ключ; MQTT EcoFlow хмарний, тож без інтернету даних однаково немає.
- Повторний вхід з іншого порту реєструє новий експортер з новим ключем: тоді введи облікові дані ще раз.

Облікові дані в `.env` і далі працюють і мають пріоритет (сторінка показує «З .env» і не може їх змінити).

### Сторінка стану експортера

Експортер сам віддає просту сторінку стану: **http://127.0.0.1:9101/** (той самий порт, що й `/healthz`; у Docker він опублікований лише на `127.0.0.1`). На ній:

- зв’язок зі станцією (MQTT), останнє повідомлення й семпл, кнопка «Reconnect»;
- стан входу в Supabase (`ok` / не виконано / відкликано / помилка) і кнопка «Log in»: та сама OAuth-авторизація, що й `login` вище, без термінала. Браузер повертається на `http://127.0.0.1:9101/callback`; якщо не повернувся (сторінка відкрита з іншої машини), встав адресу, на якій він зупинився, у поле на сторінці;
- черга запису (скільки рядків чекає, остання помилка), мережа й відкрите відключення;
- останні значення (заряд, вхід/вихід, AC, блоки й комірки) і кілька останніх відключень із Supabase.

Сторінка — чистий HTML + JS у `src/ui/` (без збірки й залежностей), дані з `GET /api/status`. Кольори, шрифти й відступи — зі спільних токенів дизайну (`src/ui/tokens.css`, [docs/uk/DESIGN.md](docs/uk/DESIGN.md)). Мова інтерфейсу англійська, кнопка «UK» перемикає на українську. Вхід зі сторінки реєструє окремий OAuth-клієнт (інша адреса повернення, ніж у `login` на `:9102`), тож на сторінці «Експортери» дашборду може з’явитись ще один рядок; старий можна відкликати.

Сторінка відповідає лише на `localhost` / IP-адреси (захист від DNS rebinding); інше ім’я хоста додай у `UI_ALLOWED_HOSTS`. Якщо порт опубліковано не на `127.0.0.1:9101`, задай `UI_URL`. Нативно експортер слухає лише `127.0.0.1`; `LISTEN_HOST=0.0.0.0` відкриває сторінку для локальної мережі (образ Docker уже слухає `0.0.0.0` всередині контейнера, а compose публікує порт на `127.0.0.1`).

Так само працює локальний домен контейнера, наприклад `https://exporter.ecoflow.orb.local` від OrbStack (`<service>.<compose project>.orb.local`): `UI_ALLOWED_HOSTS=exporter.ecoflow.orb.local`, потім створи контейнер заново (`docker compose up -d`; простий restart не підхоплює зміни `.env`). Через таке ім’я сторінка показує статус і дає натиснути «Увійти»; форма облікових даних, надсилання зразка й оновлення й далі відповідають лише на `127.0.0.1`. `UI_URL` залиш на `127.0.0.1`: сторінка згоди на дашборді повертає логін лише на loopback-адресу (захист від фішингу), тож після згоди браузер опиниться на `127.0.0.1`.

### Допомогти підтримати нову модель

Якщо експортер погано розуміє твою станцію (сторінка стану показує частку розшифрованих повідомлень), картка **«Допоможи підтримати свою модель»** на сторінці стану дозволяє поділитися, кожне з окремою згодою, показаною там же:

- **переписом моделі**: виробник, перші 4 символи серійного номера (сімейство моделі), прошивка і перелік типів повідомлень з кількістю. Без значень і повного серійного номера;
- **зразком**: записом 5–15 хвилин повідомлень станції. Серійні номери, ідентифікатор акаунта й e-mail маскуються ще до того, як щось залишить комп’ютер, також усередині XOR-нутих даних, і так само маскуються рядки, схожі на серійні номери; якщо якийсь ідентифікатор усе ж знайдено, зразок блокується. Ти бачиш підсумок (повідомлення, розмір, скільки ідентифікаторів замасковано), і нічого не надсилається, доки не натиснеш **«Надіслати»**.

Сервер вирішує, чи потрібен зразок (моделі, що вже підтримуються або мають 3 зразки, відхиляються; 1 завантаження на годину, 10 МБ). Завантажити, видалити й відкликати все можна на сторінці дашборду **«Мої дані»**. Ці кнопки працюють лише з комп’ютера, де запущено експортер (`127.0.0.1`).

### Що робить експортер

- Тримає MQTT-з'єднання, розбирає повідомлення (`src/decode/`, див. [docs/uk/DECODER.md](docs/uk/DECODER.md)) і кожні `SAMPLE_INTERVAL_S` (10 с) пише рядок у `telemetry_raw` і по рядку на кожен блок у `pack_raw`. Якщо від станції нічого не було понад 3 хв, рядки не пишуться (щоб не малювати застарілі дані).
- **Локальний буфер**: усе спершу йде в SQLite-файл (`BUFFER_PATH`, у Docker volume `buffer` → `/data`) і видаляється звідти лише після підтвердження від Supabase. Без інтернету рядки чекають і доходять потім (усі записи ідемпотентні). Ліміт 500 000 рядків, далі відкидаються найстаріші семпли (відключення ніколи).
- **Відключення** (`outages`): за прапорцем мережі від станції. Рядок вставляється, коли мережа зникла, і закривається, коли з'явилась, з SoC і віддачею в Wh. Якщо інтернет ліг разом зі світлом і MQTT мовчав, початок = останній момент, коли мережу ще бачили, кінець = перший момент, коли її знову видно. Відкрите відключення переживає перезапуск.
- **Сліпі проміжки** (`exporter_gaps`): коли від станції понад 2 хвилини нічого не приходило, проміжок записується з причиною: `sleep` (хост спав, наприклад закрита кришка ноутбука; процес помічає, що годинник стрибнув уперед), `stopped` (експортер не працював) або `offline` (працював, але нічого не отримував; справжнє відключення зазвичай забирає й інтернет). Відключення, чий початок чи кінець потрапив у такий проміжок, зберігається як вікно (`start_latest_at`, `end_earliest_at`) і показується з «≈». Якщо мережа була до і після проміжку, а заряд упав більше, ніж на холостий хід (3 пункти + 0,3 за годину), записується відключення, якого ніхто не бачив, з позначкою `inferred` на весь проміжок.
- **Watchdog**: якщо з'єднання «живе», але повідомлень немає `MQTT_SILENCE_TIMEOUT_S` (180 с), експортер перелогінюється зі свіжими кредами.
- `/healthz` (для health check контейнера) показує стан MQTT, останнє повідомлення, мережу, відкрите відключення і чергу; відповідає 503, якщо від станції нічого не було 10 хв.
- **Пакети декодерів**: нові моделі й виправлення декодера як підписані дані, ніколи не код, з хостингу дашборду (`<дашборд>/decoders/index.json` або `DECODER_INDEX_URL`). Див. [docs/uk/DECODER_PACKS.md](docs/uk/DECODER_PACKS.md).
- **Оновлення**: сторінка стану показує, коли вийшов новіший експортер (підписаний список релізів, образ закріплений за digest), і встановлює його одним натиском через окремий контейнер-оновлювач, який перевіряє походження збірки і відкочує, якщо нова версія не запустилася; сокет Docker експортер не отримує ніколи. Див. [docs/uk/UPDATES.md](docs/uk/UPDATES.md).
- **Без Docker**: один виконуваний файл для кожної ОС (Linux, macOS, Windows) з інсталятором служби. Див. [docs/uk/NATIVE.md](docs/uk/NATIVE.md).

## Образ експортера в ghcr.io

GitHub Actions (`.github/workflows/exporter-image.yml`) збирає образ експортера для `linux/amd64` і `linux/arm64` (Mac на Apple Silicon) на кожен push у `main`, що чіпає `src/`, `package*.json`, `Dockerfile`, …, і кладе його в GitHub Container Registry того репозиторію, де запущений: `ghcr.io/<owner>/<repo>`, де `<owner>/<repo>` — цей репозиторій або твій форк. Кожен запушений digest отримує build provenance attestation (див. [Перевір, що запускаєш](#перевір-що-запускаєш)).

- `deploy/docker-compose.yml` за замовчуванням бере образ цього репозиторію. `ECOFLOW_IMAGE_REPO` (наприклад `ghcr.io/<ти>/<repo>`, у shell або в `deploy/.env`) перемикає його на образ форку.
- Теги: `:main` (останній) і `:sha-<коміт>`. Зберігається не більше 3 версій (`:main` і 2 попередні), старіші видаляються після кожного push. Розмір кожної збірки видно в summary запуску (≈ 67 МБ на архітектуру).
- PR лише збирає обидві архітектури (перевірка), нічого не пушить.
- Кеш шарів: GitHub Actions cache (`type=gha`), не рахується як сховище ghcr.
- Образ береться за тегом `:main`, а не за digest: це власна збірка з цього репозиторію, а все, що всередині (базовий образ, npm), закріплено точно.
- Нові пакети в ghcr за замовчуванням приватні. Щоб будь-хто міг його стягнути без логіну, зроби пакет публічним (сторінка пакета → Package settings → Change visibility). Інакше залогінься на машині, де працює експортер, своїм акаунтом: `docker login ghcr.io -u <твій-github-логін>`, пароль — [classic token](https://github.com/settings/tokens/new?scopes=read:packages&description=ghcr%20pull) лише з правом `read:packages` (fine-grained ghcr не приймає).

## Розробка

```bash
cp .env.example .env     # локальний Supabase (SUPABASE_URL, SUPABASE_ANON_KEY); акаунт EcoFlow необов’язково
npm ci
make test                # vitest
make typecheck
make dev                 # docker compose watch: src/ синхронізується, tsx watch перезапускає; сторінка стану http://127.0.0.1:9101
```

`make` показує всі команди. Робота над декодером іде на записаних фікстурах (нижче), тож тестам не потрібні ні станція, ні мережа. Зміни в базі: [docs/uk/DB_CONTRACT.md](docs/uk/DB_CONTRACT.md).

## Залежності: точні версії і карантин 7 днів

Усе, що встановлюється, має точну версію, ніде немає `latest` чи `^`/`~`. Свіжі версії ставимо лише через 7 днів після публікації: зламані релізи (supply-chain атаки) зазвичай знаходять і відкликають раніше.

- **npm** (`.npmrc`): `save-exact=true`, `min-release-age=7` (npm ≥ 11.10 не бачить версій, молодших за 7 днів, і для транзитивних залежностей), `engine-strict=true` (npm 10 просто відмовиться ставити), `strict-allow-scripts=true` (install-скрипти залежностей виконуються лише з дозволу в `allowScripts` у `package.json`). Ставити тільки `npm ci`; нова залежність: `npm install <pkg>@<версія>`.
- **Перевірка**: `make deps-check` (`scripts/check-deps.mjs`) падає, якщо десь діапазон, lockfile розійшовся з `package.json`, або будь-який пакет у lockfile молодший за 7 днів. Те саме робить CI (`.github/workflows/ci.yml`).
- **Docker**: базові образи з точним тегом і `@sha256` digest; npm у образах закріплений.
- **Оновлення** вручну, час від часу: `make deps-outdated` показує нові версії npm-залежностей і закріплених npm-CLI (коментар `# npm-pin:`), які вже пройшли 7-денний карантин. Образи (тег + digest) і GitHub Actions (SHA коміту) оновлюються руками, теж лише на версії, старші за 7 днів.
- Нова залежність з install-скриптом (`npm install` скаже `install-scripts`): переглянь, що він робить, і `npm install-scripts approve <pkg>`.

## Структура

```
src/            index.ts (старт), server.ts + status.ts + ui/ (сторінка стану, /healthz), decode/ (protobuf → стан), model/ (спільна модель), exporter/ (семпли, відключення, буфер, запис), mqtt/, auth/ (вхід EcoFlow), oauth/ (вхід Supabase), secrets/, sources/, packs/ (підписані пакети декодера), update/ (перевірка релізів), updater/ (контейнер-оновлювач), discovery/ (перепис, зразки), proto/, db/
decoders/       пакети декодера (дані; підписує й публікує деплой дашборда)
releases/       releases.json: список релізів, який перевіряє сторінка стану (підписується так само)
test/           vitest, fixtures/ (записаний MQTT, серійники замасковані)
deploy/         docker-compose.yml (прод), docker-compose.dev.yml (watch)
packaging/      встановлювачі сервісу для однофайлових бінарників
docs/           DB_CONTRACT.md, DECODER.md, DECODER_PACKS.md, DATA_CATALOG.md, UPDATES.md, NATIVE.md, DESIGN.md; uk/ — українською
.github/        CI, образ (ghcr.io) і бінарники, з build provenance
scripts/        build-sea.mjs (бінарники), check-deps.mjs (точні версії + карантин)
```
